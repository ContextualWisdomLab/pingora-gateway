# Threat Model

## Assets

Network authority, upstream identity, availability, operator configuration integrity, request metadata, release artifacts, and consumer trust in the shared runtime.

## Principal threats and controls

| Threat | Current control | Residual gap |
| --- | --- | --- |
| Request-controlled SSRF | Upstream socket authority is startup configuration only; generic v1 admits one fixed upstream and the bounded pg-erd profile admits only characterized `backend`/`frontend` identities | Config write compromise remains privileged; future discovery/dynamic resolution must preserve the same fail-closed authority boundary |
| Recursive self-proxy / metrics-surface routing | Traffic and metrics listeners cannot overlap; admitted upstreams also cannot overlap either gateway-owned listener under exact, wildcard, or conservative IPv6-wildcard/IPv4 dual-stack authority semantics | Exact-head hosted execution of the new source contract is still pending; this control does not replace deployment-network ACLs for metrics |
| TLS MITM/upstream impersonation | Explicit upstream SNI plus certificate/hostname verification; optional operator trust bundle is materialized once before listeners open | Successful pg-erd TLS-listener parity and downstream TLS are not yet proven |
| Forwarded-header spoofing | Generic v1 strips the full request-controlled forwarding identity set and emits only gateway-owned `Forwarded: proto=http`; the bounded migration policy rebuilds characterized compatibility fields from accepted transport/request authority | No trusted-proxy/client-IP chain feature; HTTPS needs a separate TLS-derived scheme contract |
| Uncharacterized HTTP/1 protocol transition | Generic v1 and the bounded pg-erd candidate reject an `Upgrade` field or an `upgrade` token in `Connection` as HTTP 501 before application admission, route/upstream selection, or origin contact; real-listener acceptance covers both composition roots | WebSocket remains intentionally unsupported by the current contract. Any later admission requires consumer-derived semantics, disposition/backport of open Pingora issue #946/#947, realistic concurrency/tunnel/disconnect/backpressure/drain evidence, and separate HTTP/2 Extended CONNECT semantics; HTTP/3/QUIC remains separate |
| Request-body / header-parser / concurrency exhaustion | Explicit declared and streamed body limits; mandatory process-wide in-flight admission fails fast at 503 while health/metrics remain reachable; pinned Pingora HTTP/1 still supplies finite parser ceilings (`MAX_HEADERS = 256`, `MAX_HEADER_SIZE = 1_048_575`) | The HTTP/1 ceilings are supplier-fixed rather than operator-configurable. A callback-only 431 occurs after header buffering/parse and is not parser-phase resource admission. `pingora-gateway#43` / `cloudflare/pingora#993` track a supported smaller H1 byte/count budget; HTTP/2 decoded-header-list accounting remains a separate protocol contract. Connection/per-route admission and broader deployment resource budgets also remain gaps |
| Incomplete downstream HTTP/1 request-header lifetime | Pinned Pingora defaults downstream H1 `read_timeout` to 60 s, so a connection that sends no request-header bytes is bounded by inactivity | The timeout is per read, not a monotonic whole-header budget. Successful partial reads can refresh the wait and keep an incomplete header in progress beyond 60 s. `pingora-gateway#45` and `cloudflare/pingora#447` track a supported whole-header deadline; callback handling, a retained front proxy, or a mutable supplier fork is not closure |
| Slow/dead/aborting upstream | Explicit connect/total-connect/read/write/idle budgets plus source acceptance for refused origin, connected-silent read timeout, orderly truncated response, pre-header TCP RST and post-commit TCP RST. Pg-erd config v2 additionally requires a monotonic `max_upstream_response_body_ms` progress lifetime that does not reset on body progress; no automatic replay/failover is invented. Bounded-origin source acceptance characterizes four-worker origins with 16 VUs / 1600 routed requests and aggregate plus per-route p95 `<20 ms` loopback gates | The body lifetime is progress-driven and cannot interrupt a pending supplier read at the exact deadline. Continuously progressing incomplete HTTP/1 response headers remain a separate overall-header-deadline gap on `pingora-gateway#40` / `cloudflare/pingora#992`; arbitrary admitted long-lived streaming and representative production-origin/TLS/network/deployment capacity evidence remain open |
| Hop-by-hop/request smuggling ambiguity | Pingora standard policy strips hop-by-hop/connection-nominated headers; exact dependency source is pinned, the gateway adds explicit forwarding-identity handling, and unsupported HTTP/1 Upgrade is rejected instead of silently inheriting supplier transition behavior | Supplier advisory disposition and authoritative Dependency Review evidence remain release blockers; any future protocol transition needs its own parser/transition security analysis, including RFC 9931 |
| Credential or product-data leakage in shared telemetry | Shared observability emits bounded status/outcome/body-byte facts and low-cardinality counters; dedicated compiled pg-erd acceptance sends non-vacuous URI/query/Host/Authorization/Cookie/product-context sentinels and requires none in the canonical shared log target | Distributed tracing is not yet implemented; consumer/product logging remains outside this bounded context |
| Request-secret leakage through dependency diagnostics | Production composition roots install the shared `logging_policy`; operator `RUST_LOG` still selects verbosity, but every Pingora-family record has its message body replaced with a static marker before formatting. A compiled generic process test runs with `RUST_LOG=trace`, proves the origin received URI/Authorization/Cookie sentinels, and requires none of them in process stderr | Exact-head hosted execution is pending. Future dependencies that can format request material must be classified into the same process logging boundary before adoption |
| Container privilege/persistence | Digest-pinned distroless image, uid/gid 65532, read-only root, capabilities dropped, `no-new-privileges`, read-only configuration; both composition roots have exact OCI source acceptance | Current exact-head hosted OCI execution and immutable published digest/provenance are still required |
| Supply-chain substitution / known vulnerable graph | `Cargo.lock` committed; `--locked` build/test policy; exact Pingora revision; SBOM/image-vulnerability/provenance gates exist | `derivative 2.2.0` / `RUSTSEC-2024-0388`, exact-release versus patched-`lru` policy, and public non-fork Dependency Review HTTP 403 remain fail-closed release blockers |
| Unsafe rollout | Draft/pre-traffic stack, process health, source acceptance for routed graceful drain, explicit parity -> shadow/canary -> cutover -> rollback sequence | No immutable protected release, consumer shadow/canary, cutover, rehearsed rollback or legacy-removal evidence yet |

## Abuse cases explicitly out of scope

Open forward proxying, arbitrary user-provided destinations, certificate issuance, consumer authentication/business authorization, product route decisions, Wardnet/EgressWeave verdict duplication, and Keyverse identity ownership are rejected as ownership violations rather than implemented generically. WebSocket or another protocol transition is not an abuse case, but it remains outside the admitted v1/pg-erd capability until its own versioned traffic and supplier-safety evidence exists.
