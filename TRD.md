# Technical Requirements

## Runtime

Rust edition 2021 with minimum Rust `1.98.0`. Pingora and `pingora-prometheus` are pinned to the exact upstream Git revision declared in `Cargo.toml`. The generic production composition root is `src/bin/cwl-pingora-gateway.rs`: it requires `--config`, validates `GatewayConfig`, constructs `GatewayProxy`, binds the explicit traffic and metrics listeners, and delegates lifecycle handling to Pingora `Server`. The separate `src/bin/cwl-pingora-pg-erd-migration.rs` composition root uses the same explicit command-line config path but admits only the bounded `PgErdMigrationConfig` profile and its prevalidated `MigrationGatewayProxy`; it is a migration candidate, not a protected release or consumer cutover.

## Generic edge contract

Configuration version 1 is strict YAML with unknown fields rejected. The generic aggregate requires an explicit non-zero traffic listener, a distinct non-zero metrics listener, positive `max_request_body_bytes`, `max_in_flight_requests`, and `upstream_keepalive_pool_size`, plus exactly one explicit upstream. Listener/metrics network authority rejects equal sockets, same-port wildcard aliases, and the platform-dependent IPv6-wildcard/IPv4 same-port overlap while preserving distinct concrete non-zero IP authorities. Every admitted upstream must also remain disjoint from both gateway-owned listeners under the same effective socket-authority semantics.

Each upstream has a stable name, concrete non-zero socket address, `tls`, optional `sni`, optional absolute PEM trust-bundle path, and explicit positive connection/total-connection/read/write/idle timeout budgets. TLS upstreams require SNI; cleartext upstreams reject SNI and custom trust bundles. Peer materialization keeps certificate and hostname verification enabled and uses HTTP/1.1 upstream transport for the current contract. No downstream request may choose an upstream dynamically. Pingora `read_timeout` remains a per-read inactivity timer, not an overall response deadline; generic v1 therefore still has no response-body lifetime contract.

## Bounded pg-erd migration config

`PgErdMigrationConfig` is not a generic multi-route language. Version 1 remains the existing unreleased characterization profile. Version 2 is a narrow runtime-isolation increment: it accepts the same deployment-variable listener/metrics sockets, positive body/in-flight/keepalive budgets, and concrete transport/TLS bindings for the fixed `backend` and `frontend` identities, and additionally requires a positive explicit `max_upstream_response_body_ms`. Version 1 rejects that field, so timing semantics cannot change without changing the configuration version. Route precedence, response-security policy, admitted upstream names, product authentication/authorization, service discovery, and business routing are not operator-configurable. Parsing validates authority without loading trust bytes; `build_proxy` materializes all peers and custom trust before listeners may obtain network authority. Both admitted pg-erd upstreams must remain disjoint from traffic and metrics listener authority under the shared exact/wildcard/dual-stack overlap rule.

Downstream TLS/ALPN is not part of generic v1 or pg-erd v1/v2. Both current application composition roots construct `http_proxy_service` and bind the application socket with `add_tcp`; neither loads listener certificate/key material nor configures downstream ALPN. Issue #51 and Proposed ADR 0012 own the later configuration-version transition. Upstream TLS fields must never be reinterpreted as downstream termination configuration.

## Request and forwarding policy

Pingora's standards-oriented upstream request policy strips standard hop-by-hop fields, strips connection-nominated extension fields, and rejects malformed protected nominations. For the current CWL contract, `pingora_delivery` constructs every immutable upstream peer with `HttpUpstreamRequestPolicy::deny_upgrades()` rather than Pingora's `standard()` default. This preserves the standard hop-by-hop and nomination sanitization while making the transport adapter itself deny HTTP/1 Upgrade forwarding. The peer-level denial is defense in depth beneath the gateway-owned request admission rule; it is not a WebSocket implementation or a product-routing decision.

Generic v1 additionally removes request-controlled `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Port`, `X-Forwarded-Proto`, `X-Forwarded-Server`, and `X-Real-IP`, then emits only gateway-owned `Forwarded: proto=http`; generic v1 deliberately does not assert client identity.

The pg-erd migration uses the separate `forwarding_policy` trust boundary. It discards the same request-controlled forwarding identity and reconstructs only the characterized compatibility fields from accepted downstream transport and request authority. Because the captured legacy entryPoint is clear-text `web`, the current migration scheme is explicitly `http`; HTTPS requires #51's separate downstream TLS contract and must derive scheme from accepted TLS state rather than a request-controlled header or a reused hard-coded value.

Requests with a parseable `Content-Length` larger than `max_request_body_bytes` fail with HTTP 413 before upstream selection. Streamed chunks are counted against the same bound and fail with HTTP 413 when the cumulative body crosses it. Non-health application requests share the process in-flight admission budget and fail fast with HTTP 503 when it is exhausted; `/livez` and `/readyz` remain outside that application-capacity budget.

At pinned Pingora `09696b51bc59315353d96686355861604d0bb48c`, HTTP/1 request-header parsing is finite but not operator-configurable through the supported server/composition API: the supplier parser uses `MAX_HEADERS = 256`, `INIT_HEADER_BUF_SIZE = 4096`, and `MAX_HEADER_SIZE = 1_048_575`. A callback-only size check in `ProxyHttp::request_filter()` would run after `RequestHeader` construction and therefore can provide semantic rejection but cannot be credited as a parser/pre-allocation resource-admission bound. HTTP/2 uses separate decoded-header-list accounting through `H2Options::max_header_list_size`; its limit is not interchangeable with HTTP/1 wire/parser bytes. The missing supported HTTP/1 parser-phase admission hook is tracked by `pingora-gateway#43` and supplier `cloudflare/pingora#993`. No new Admin Config field is admitted until a supported immutable/provenance-bound supplier capability exists. Per-route admission remains a separate gap; representative production-origin capacity remains a deployment evidence gap rather than an operator request-limit field.

Downstream HTTP/1 request-header lifetime is a separate invariant from byte/count admission. At the same pinned supplier revision, a new H1 session defaults `read_timeout` to 60 seconds and request-header reads use that timeout when no keepalive timeout applies, which bounds a connection that sends no header bytes. It is still a per-read inactivity budget: `read_request()` can continue after each successful partial read, so an incomplete slow-drip header can occupy connection/parser resources beyond 60 seconds. `HttpProxy::handle_new_request()` awaits completion of `downstream_session.read_request()` before `ProxyHttp` callbacks, so `early_request_filter`/`request_filter` cannot impose a pre-complete-header lifetime. `pingora-gateway#45` and existing supplier issue `cloudflare/pingora#447` track a supported monotonic whole-header deadline, distinct from #43/#993. No callback watchdog, retained Nginx layer, or mutable supplier fork is credited as closure.

Pg-erd config version 2 starts its monotonic response-body lifetime in `upstream_response_filter` on the first non-informational upstream response header, before body-progress callbacks are processed. Each `upstream_response_body_filter` progress callback rejects an elapsed lifetime at or beyond `max_upstream_response_body_ms` as an upstream-scoped fatal error. This complements, rather than replaces, the per-read `read_ms` inactivity timer. With the pinned Pingora callback API the body-lifetime guard is progress-driven: it stops continuous slow-drip at the first body callback after the deadline, while a quiescent pending read can run until `read_ms`. It therefore must not be described as an exact timer interrupt. Slow-drip of an incomplete response header remains a separate transport gap.

## Downstream TLS and HTTP/2

Current source is deliberately RED for downstream TLS/H2 parity. `cwl-pingora-gateway` and `cwl-pingora-pg-erd-migration` both bind application traffic with Pingora `add_tcp`; no listener certificate/key reference, SNI mapping or ALPN policy exists. This is distinct from the already-tested gateway-to-upstream TLS path. The pinned supplier provides supported TLS listeners and H1/H2 server sessions, so a later versioned contract may use those APIs rather than copying supplier transport internals.

The current upstream transport remains `ALPN::H1`. Therefore enabling downstream H2 would exercise H2-downstream -> H1-upstream translation. That mixed-protocol boundary is a release prerequisite, not an implementation detail. Open supplier `cloudflare/pingora#935` reports that a streamed H2 request ending with an empty DATA frame carrying END_STREAM can cause the H1 chunk terminator to be written twice and poison a pooled keep-alive connection. Open PR #936 makes zero-length chunked writes no-ops in both async and cancel-safe task paths but is not a maintainer-integrated immutable dependency. Open #892 reports that multiple H2 `Cookie` fields are not concatenated with `; ` before entering an H1 context as required by RFC 9113 §8.2.3; that report must be reproduced or disproved on the exact supplier used by the candidate.

A downstream TLS/H2 GREEN must therefore:

- introduce an explicit positive versioned listener-side TLS/ALPN contract, consume provisioned certificate/key material read-only, reject invalid authority before listener activation, and keep issuance/renewal/ACME/private-key backup outside this repository;
- use TLS ALPN for HTTPS H2 and keep plaintext h2c separately disabled unless a consumer explicitly characterizes it;
- prove real TLS identity/SNI and deliberate HTTP/1.1 fallback with an ephemeral local CA/certificate against the compiled listener;
- prove HTTP/2 concurrent streams, decoded-header-list boundaries, request-body bounds, stream cancellation/reset, connection-level GOAWAY/drain, origin failure, readiness, observability and independent recovery;
- while upstream remains H1, send a streamed H2 request ending in empty DATA+END_STREAM, observe exactly one H1 chunk terminator, reuse that same upstream keep-alive connection for an unrelated request, and verify exact multiple-`Cookie` normalization plus pseudo/hop-by-hop translation on the H1 wire;
- keep upstream H2 as a separate versioned origin/transport decision rather than switching ALPN to avoid the mixed-protocol RED;
- measure new TLS handshakes and reused connections separately under realistic concurrency without reducing sample size or excluding the relevant handshake/routing I/O from the buyer-facing measurement.

HTTP/3/QUIC remains unsupported and uncredited. The current public supplier evidence does not establish a first-class H3 server path equivalent to H1/H2. A custom ALPN string, an external legacy front proxy, or a vendored QUIC stack cannot be counted as #51 closure. A later H3 contract requires a separately accepted immutable transport dependency plus UDP exposure/network policy, QUIC TLS/ALPN, QPACK/header limits, stream/connection flow control, congestion/loss behavior, amplification protection, connection migration, explicit fail-closed 0-RTT replay policy, drain/close and rollback traffic evidence under RFC 9114/9000/9001.

Current normative authority is RFC 9846 for TLS 1.3, RFC 9525 for service identity, RFC 9113 for HTTP/2, RFC 9114 for HTTP/3, and RFC 9000/9001 for QUIC/TLS. RFC 9846 obsoletes RFC 8446; new traceability must not reintroduce RFC 8446 as the current TLS 1.3 normative reference.

## Protocol-transition admission

HTTP/1 connection-wide protocol transitions are not part of generic v1 or the bounded pg-erd candidate. A request containing an `Upgrade` field, or containing a case-insensitive `upgrade` token in any comma-delimited `Connection` field value, fails with HTTP 501 before application admission, route/upstream selection, or origin contact. Unrelated tokens such as `x-upgrade` do not match. Gateway-local `/livez` and `/readyz` remain local HTTP responses and therefore do not acquire origin network authority. Independently, every materialized Pingora peer uses `HttpUpstreamRequestPolicy::deny_upgrades()`, so a later callback or composition refactor cannot silently fall back to Pingora's default `H1UpgradePolicy::WebSocketOnly` below this admission boundary.

This fail-closed policy is intentional rather than a claim that WebSocket is unsupported by Pingora in general. RFC 9110 §7.8 allows a server to decline an HTTP/1.1 Upgrade. RFC 6455 defines WebSocket's HTTP/1.1 opening handshake, while RFC 8441 defines HTTP/2 WebSocket bootstrap through Extended CONNECT rather than connection-wide Upgrade. RFC 9931 (March 2026) adds current security requirements and analysis for optimistic HTTP/1.1 protocol transitions. The pinned Pingora source also has open supplier issue `cloudflare/pingora#946`, where a scheduler ordering can tear down a WebSocket tunnel immediately after a successful `101`; proposed fix `cloudflare/pingora#947` is still unmerged as of the current evidence sweep. A later WebSocket increment therefore requires a versioned consumer-derived contract, an immutable supplier disposition or reviewed backport, realistic handshake/tunnel concurrency, disconnect/backpressure/drain evidence, and separate HTTP/2 semantics where applicable. HTTP/3/QUIC remains separate.

## Health, observability, retry, and drain

`/livez` and `/readyz` produce an empty non-cacheable HTTP 200 through the Pingora serving path. Readiness proves admitted configuration plus an active process serving path, not upstream health. Shared observability records only low-cardinality status/outcome/body-byte and backpressure facts; paths, query strings, headers, cookies, credentials, customer payloads, and product identifiers are outside the shared telemetry contract.

The version-1 process policy allows one total upstream attempt and therefore no automatic gateway retry. It overrides Pingora's keepalive-pool default from validated configuration and uses a 5-second grace period plus 10-second Pingora runtime shutdown timeout inside a 30-second external termination budget. Product idempotency/replay policy remains outside the gateway.

Existing source acceptance proves graceful completion for an already-admitted in-flight request, but it does not prove prompt shutdown of downstream HTTP/1 connections parked in `read_request()`. At protected public Pingora `09696b51bc59315353d96686355861604d0bb48c`, each `HttpProxy` instance owns one shared `tokio::sync::Notify` for the parked HTTP/1 reads handled by that instance; `handle_new_request()` does not consult the existing shutdown flag before parking on `shutdown.notified()`. Upstream #844 is Accepted only into Cloudflare's internal line and reports severe many-core waiter-list contention; public repair #969 remains open/unmerged and independent review reproduces the lost-wakeup race on the public main. `pingora-gateway#46` therefore keeps parked-read wakeup correctness and many-core shutdown scaling as a separate supplier-bound Runtime Isolation requirement. A later GREEN must preserve the current in-flight grace semantics while proving repeated race-safe parked-read termination and realistic worker/concurrency scaling on an immutable supplier/release identity; a contributor-branch pin or gateway-local copy of `pingora-proxy` internals is not admissible.

Failure semantics are phase-aware. Before an upstream response header is committed downstream, transport failure may be represented as the gateway's fail-closed error response under the configured attempt policy. After a valid response header has already been committed, a later upstream framing/body failure—including a version-2 response-body lifetime breach—cannot be rewritten into a second HTTP status or silently failed over; the downstream response is terminated, low-cardinality error telemetry records the failed request, process readiness remains available, the request context releases its in-flight lease, and independent routes must remain usable. This is a transport invariant, not product retry policy.

## Performance evidence

The exact-head CI load lane uses checksum-pinned k6 2.2.0 against release binaries. Generic v1 and the bounded pg-erd composition root each retain a separate 400-request/four-VU loopback contract with zero request failures and `http_req_duration` p95 below 20 ms. The pg-erd low-contention contract keeps `backend` and `frontend` as distinct local authorities and alternates characterized backend and fallback routes so the measurement includes multi-route selection and response policy on the bounded binary.

Draft PR #42 adds a separate bounded-origin capacity/connection-churn regression rather than replacing that baseline. Two std-only Rust origins run with four workers each, a bounded accept queue, `Connection: close`, and 1 ms startup-configured service delay. The exact release-mode pg-erd binary receives 1600 requests across 16 VUs, with exact route-body assertions, zero check/HTTP failures, aggregate `http_req_duration` p95 below 20 ms, and independent backend/frontend tagged p95 bounds below 20 ms. A one-worker/150 ms direct-origin socket self-check must first prove actual serialization and exact close framing, and no application route is warmed before measurement.

These gates are controlled local regression bounds only; they do not establish a production SLO. Representative production-origin capacity, TLS, network/multi-hop, container/orchestrator, and consumer deployment measurements remain required before a 20 ms p95 production objective may be claimed. Issue #46 adds a distinct supplier/runtime performance requirement: high-core parked-read shutdown registration/unregistration must be profiled at the largest available realistic Linux/NUMA worker topology before claiming the shared-`Notify` bottleneck is removed. Reducing worker count, parked connection count, or keep-alive use merely to avoid contention is not equivalent evidence. Issue #51 adds a distinct downstream protocol path: TLS handshake and H2 multiplexing/translation must be measured without transferring clear-text H1 p95 credit or hiding handshake cost behind unrealistic session warm-up.

## Packaging and release evidence

The OCI runtime executes as uid/gid `65532`, is compatible with read-only-root and capability-free operation, and relies on digest-pinned base images. The exact image packages both the generic and bounded pg-erd composition roots while retaining the generic binary as the default entrypoint; dedicated pg-erd invocation under uid/gid 65532, read-only root, dropped capabilities, `no-new-privileges`, read-only configuration, process-health, and metrics constraints has source acceptance but still requires terminal exact-head OCI execution. A committed lockfile, exact-head test/coverage/rustdoc/load/security/supply-chain evidence, immutable image digest, SBOM/provenance/reproducibility, rollback rehearsal, and protected integration remain release gates. Source-level migration capability is not parity, canary, cutover, rollback, or legacy-removal evidence. Supplier issue #46 remains release-blocking for the parked-read shutdown claim until a maintainer-integrated immutable/released capability or separately governed provenance-bound backport is exercised through the required race/concurrency acceptance. Downstream TLS/H2 is separately release-blocked by #51 until its consumer characterization, supplier mixed-protocol translation gates, versioned configuration, real listener traffic and immutable dependency evidence are terminal; HTTP/3/QUIC remains explicitly unsupported rather than inherited from external infrastructure.
