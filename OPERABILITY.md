# Operability and Recovery

## Start

Run the generic process as `cwl-pingora-gateway --config /path/to/gateway.yaml`. Configuration is read and validated before the listener is registered. Invalid or missing configuration exits non-zero. `max_request_body_bytes`, `max_in_flight_requests`, and `upstream_keepalive_pool_size` are mandatory positive deployment inputs; the process will not start with a zero value or silently inherit a Pingora keepalive default. If a TLS upstream declares `trust_bundle_file`, that absolute PEM bundle is read and parsed during peer activation before listeners open; unreadable, empty, or malformed trust material prevents activation.

The pg-erd migration candidate is a separate executable: `cwl-pingora-pg-erd-migration --config /path/to/pg-erd-migration.yaml`. It consumes the bounded `PgErdMigrationConfig` profile rather than widening generic `GatewayConfig` v1. The profile admits exactly the compiled `backend` and `frontend` transport identities plus deployment-variable sockets, runtime budgets and upstream transport/TLS values. Route tables, response-policy fields, product authentication/business rules, Keyverse identity, Wardnet/EgressWeave verdicts, service discovery and arbitrary destinations are not operator-configurable.

Pg-erd configuration version 1 preserves the existing unreleased characterization behavior and has no response-body lifetime. Version 2 is opt-in and requires a positive `max_upstream_response_body_ms`; version 1 rejects that field rather than silently acquiring new timing semantics. Choose the version-2 value from observed application long-response requirements before canary or cutover. Documentation/example values are not production SLOs. A zero or incomplete version-2 budget fails before listeners open.

Neither generic v1 nor pg-erd v1/v2 currently exposes an operator-controlled downstream HTTP/1 request-header byte/count budget. Pinned Pingora enforces finite supplier ceilings before the proxy callback, but those fixed parser limits are not CWL Admin Config and cannot be lowered from `ProxyHttp::request_filter()` after `RequestHeader` construction. Do not represent a callback-only 431 response, an Nginx/Traefik front proxy, or a locally edited Pingora parser as closure of this resource-admission gap. `pingora-gateway#43` and supplier `cloudflare/pingora#993` own the supported parser-phase capability path; HTTP/2 decoded-header-list accounting remains a separate protocol contract.

The same HTTP/1 downstream path also lacks an operator-controlled whole-request-header lifetime. Pinned Pingora's 60-second `read_timeout` bounds an individual idle read, not the entire in-progress header sequence; successful partial reads can continue the parser loop and receive another relative wait. Do not tune a tiny global read timeout and call that equivalent to a whole-header budget, and do not rely on `early_request_filter` or `request_filter`, which are reached only after request-header parsing. `pingora-gateway#45` and existing supplier issue `cloudflare/pingora#447` own a supported monotonic header-sequence deadline. Keep idle-between-requests behavior, header-in-progress lifetime, #43/#993 byte/count admission, and #40/#992 upstream response-header lifetime as separate operator contracts.

Admin parsing is side-effect free with respect to custom trust bytes. It validates the exact transport-authority set and `UpstreamConfig` invariants first. `build_proxy` then materializes Pingora peers and any custom PEM trust bundle once, still before listener registration. This avoids reading mutable trust material in a validation pass and reading it again for activation.

Trust bundles are deployment input, not certificate-authority ownership. Mount them read-only from the platform or canonical secret/certificate owner and rotate them by replacing the deployment revision. The gateway does not issue certificates, manage ACME, or write trust material.

Downstream TLS is not an existing operator field. Both production composition roots still bind application traffic with Pingora `add_tcp`, and every currently materialized upstream peer remains `ALPN::H1`. `pingora-gateway#51` and Proposed ADR 0012 therefore require a separate configuration-version transition for listener-side certificate/key references, SNI mapping and ALPN admission. Those references are consumed read-only; certificate issuance, renewal, ACME account state, private-key backup and product identity remain with their canonical owners. An operator must not repurpose upstream `sni`/`trust_bundle_file`, place a legacy TLS proxy in front and count it as shared-gateway parity, or enable plaintext h2c as a shortcut for HTTPS HTTP/2.

## Health, backpressure, and response lifetime

Both process identities reserve `/livez` and `/readyz` and return 200 with `Cache-Control: no-store` through the Pingora serving path. Readiness is process/configuration readiness, not upstream reachability. Do not use it as proof that a dependent application is healthy. For the pg-erd migration, consumer `/healthz` remains routed application traffic to `backend`; it is intentionally distinct from the gateway-local probes.

`max_in_flight_requests` limits concurrently admitted non-health requests for one gateway process. At capacity the gateway fails new application traffic fast with HTTP 503 and increments `cwl_pingora_gateway_backpressure_rejections_total`; it does not queue unbounded work. Process health probes bypass that admission budget so operators can distinguish process health from traffic saturation. The request lease is released when the Pingora request context ends, including error paths, and a subsequent request is admissible again.

For pg-erd version 2, `max_upstream_response_body_ms` limits the elapsed body phase after the first non-informational upstream response header. It complements the peer's `read_ms`; it does not replace it. `read_ms` remains a per-read inactivity timeout that resets whenever Pingora successfully reads more upstream data. Continuous response-body slow-drip is stopped at the first body-progress callback at or beyond the explicit body lifetime, producing an upstream-scoped request error. If HTTP status/headers were already committed, the gateway terminates that incomplete response rather than sending a second status or switching to `frontend`. The request context then releases its in-flight lease.

This control is not an exact wall-clock interrupt. With the pinned Pingora callback API, an already pending read is not awakened solely because the body-lifetime instant elapsed; a quiescent response remains bounded by `read_ms`, and continuously progressing traffic is checked when body progress reaches the callback. Slow-drip of an incomplete response header is still a separate gap. Do not advertise the configured number as a strict production deadline until representative deployment traffic has measured the actual scheduler/read-callback behavior.

`upstream_keepalive_pool_size` is copied into Pingora `ServerConf` before bootstrap. Choose it with expected upstream concurrency, origin capacity, instance count and connection reuse in mind. It limits retained reusable upstream connections; it is not a substitute for the downstream in-flight admission limit and does not create product-domain load-balancing semantics.

## Forwarding and protocol boundary

The generic v1 adapter and the pg-erd migration adapter have different compatibility forwarding contracts. Generic v1 strips inbound proxy-identity fields and emits only `Forwarded: proto=http`. The pg-erd migration adapter removes request-controlled `Forwarded`, `X-Forwarded-*`, `X-Real-IP` and legacy `X-Forwarded-Server` authority, then rebuilds only the characterized `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Host`, `X-Forwarded-Port`, and `X-Forwarded-Proto` fields from accepted downstream transport/request authority. Product identity, tenant identity and authorization are never derived from these transport fields by the shared gateway.

The captured pg-erd Traefik entryPoint is clear-text `web`, so this migration profile currently uses downstream scheme `http`. HTTP/1 Upgrade attempts are rejected before origin contact by the current versioned contract. Do not deploy this profile behind a TLS listener and assume `X-Forwarded-Proto: https` parity. When #51 eventually admits downstream TLS, `https` must be derived from accepted TLS state rather than request-controlled forwarding data or the current hard-coded clear-text characterization.

Downstream HTTP/2 is also not a listener-only operational toggle. Because current upstream peers remain `ALPN::H1`, the first admitted H2 request crosses an H2-downstream -> H1-upstream translation boundary. Before enabling H2 in any environment credited toward migration, the exact immutable supplier must pass the #51 mixed-protocol traffic contract: streamed request completion with an empty DATA+END_STREAM tail must generate exactly one H1 chunk terminator, the same H1 keep-alive connection must serve an unrelated follow-up request, multiple H2 `Cookie` fields must enter the H1 context with RFC 9113 §8.2.3 `; ` coalescing, and pseudo/hop-by-hop translation, reset/cancel, GOAWAY/drain and recovery must remain bounded. `cloudflare/pingora#935/#936` is the concrete supplier path for the duplicate-terminator/desynchronization defect; #892 remains a mandatory exact-supplier Cookie characterization/disposition. Do not switch the upstream protocol to H2 simply to make this RED disappear; upstream protocol selection is a separate origin compatibility and pooling decision.

HTTP/3/QUIC remains unsupported and uncredited even after TLS/H2 work becomes GREEN. An external Nginx/Traefik H3 listener, a custom ALPN string, or a separately vendored QUIC stack does not establish shared-runtime parity. A later H3 increment requires its own immutable transport dependency, UDP exposure/network policy, QUIC TLS/ALPN, QPACK/header limits, flow control, loss/congestion, amplification protection, connection migration, explicit 0-RTT replay policy, drain/close and rollback evidence.

## Logging

Both production composition roots install the shared payload-safe runtime logger before configuration or listener activation. `RUST_LOG` still selects normal levels and targets, so `RUST_LOG=cwl_pingora_gateway::observability=info` remains appropriate for routine coarse access logs and an operator may request broader diagnostics while investigating an incident.

Pingora-family dependency records are a deliberate exception: their message bodies are replaced with a static marker before `env_logger` formats them. The pinned supplier contains diagnostic paths that can format request URI, Host and full request headers, so forwarding those messages verbatim would let a broad `RUST_LOG` setting bypass the gateway's no-credentials/no-cookie/no-request-route logging invariant. The redaction keeps target and level visible for correlation but does not expose the supplier message body. Do not treat `RUST_LOG=trace` as an escape hatch for request inspection; use purpose-bound consumer/application diagnostics at their canonical owner instead.

## Retry and shutdown

The runtime does not inherit Pingora's retry, keepalive-pool, or drain defaults. `src/runtime_policy.rs` sets Pingora's `max_retries` field to `1`; in the pinned proxy loop that value means one total upstream attempt, so the shared generic edge performs no automatic retry. The pg-erd composition root uses the same server policy. Retry policy requires request-idempotency knowledge and stays with a later explicit contract rather than being inferred by the gateway.

SIGTERM uses Pingora graceful termination with an explicit 5-second request-drain grace period and a 10-second runtime-shutdown timeout. The pinned Pingora server calls Tokio `Runtime::shutdown_timeout` with that timeout and then sleeps for the same timeout while service runtimes are shut down in parallel. The policy therefore requires a 30-second supervisor hard-kill budget: its modeled worst-case Pingora process budget is 25 seconds plus scheduler/process-exit overhead. A Kubernetes-style deployment must set `terminationGracePeriodSeconds` to at least 30 or provide an equivalent supervisor budget; a shorter external kill deadline is not an admitted deployment contract.

That external fallback does not make prompt shutdown of parked HTTP/1 reads proven. Public Pingora `09696b51bc59315353d96686355861604d0bb48c` still places the parked HTTP/1 read waiters handled by a given `HttpProxy` instance on that instance's one shared `tokio::sync::Notify`; a shutdown can fire before a newly pending read has registered its waiter, and the existing `shutdown_flag` is not checked on that path before parking. Upstream `cloudflare/pingora#844` reports severe many-core contention on the same per-`HttpProxy` waiter list and is only Accepted into Cloudflare's internal line. Public repair #969 is open/unmerged; independent review reproduces the lost-wakeup on the pinned public main and also identifies contributor-branch integration concerns. `pingora-gateway#46` owns this separate operator/release gap. Do not shrink the external grace so the survivor is killed sooner, disable keep-alive, reduce workers/connections until contention disappears, pin #969 directly, or copy `pingora-proxy` internals into the gateway and call that a production repair.

`tests/graceful_shutdown.rs` exercises the generic compiled binary with a held upstream response. `tests/production_path.rs` covers generic saturation, health and failure recovery. `tests/pg_erd_production_path.rs` exercises the dedicated pg-erd process with real loopback backend/frontend origins, including process-local health, characterized route/response-header behavior, transport-derived forwarding replacement and declared body rejection. `tests/pg_erd_slow_drip_response_traffic.rs` separately proves the version-2 body-lifetime behavior with progress faster than `read_ms`. `tests/pg_erd_binary_startup.rs` requires missing/invalid configuration and unreadable trust material to fail before listener activation. `tests/pingora_diagnostic_log_safety.rs` runs the compiled generic process with broad trace diagnostics and requires request URI/Authorization/Cookie sentinels to reach the origin without appearing in process stderr. These source contracts become evidence only after terminal success on the exact current head; predecessor success never transfers.

Existing graceful-shutdown tests cover admitted in-flight work, not new/reused downstream connections parked in `read_request()`. #46 RED must reproduce the one-shot lost-wakeup at the exact integrated supplier revision by jittering shutdown around waiter registration under both production composition roots, while separately measuring realistic many-worker/many-keepalive contention. GREEN requires zero parked-read survivors beyond the bounded shutdown expectation across repeated adversarial runs, continued successful completion of admitted in-flight requests inside the grace, healthy startup/recovery semantics, and high-core profiling at the largest available Linux/NUMA-capable environment before claiming the contention bottleneck removed. Request paths, headers, cookies and payloads are unnecessary for this evidence.

No compiled real-listener test yet proves a downstream incomplete request header is terminated by a monotonic whole-header budget while fragments continue arriving. That RED belongs to #45 and must remain below the configured/future byte-count admission ceiling so a later GREEN cannot accidentally pass because of #43. A supported supplier capability from/disposition of #447 is prerequisite to claiming the runtime repair; the current documentation records the missing control rather than simulating it in application callbacks.

No compiled real-listener test yet proves #51 downstream TLS/H2 parity. The RED must first preserve the existing current behavior—both composition roots are clear-text application listeners—and then a versioned candidate must use an ephemeral local CA/certificate to prove accepted SNI/identity, ALPN negotiation and intentional H1 fallback. H2 acceptance must exercise concurrent streams, decoded-header-list and request-body bounds, reset/cancel, GOAWAY/drain, origin failure and independent recovery, together with the H2->H1 wire checks above. New-handshake and reused-connection performance must be measured separately at realistic concurrency. These tests must not be simulated by a retained front proxy or by changing upstream ALPN.

## Container

Run as a non-root user and prefer a read-only root filesystem. Mount only the versioned config and any required upstream trust bundle read-only. The runtime does not intentionally write logs or state files; stdout/stderr should be collected by the platform. Do not bake secrets or private keys into the image or config.

A future downstream TLS version must retain this isolation model. Provisioned certificate/key material must be mounted through the canonical secret/certificate owner with the minimum readable scope, never baked into the image, logged, copied to evidence artifacts, or treated as writable gateway state. HTTP/3 would additionally require explicit UDP/Kubernetes exposure evidence rather than silently widening the current TCP-only deployment contract.

The Dockerfile and OCI gate package both Rust composition roots in the same digest-pinned image while retaining `cwl-pingora-gateway` as the default entrypoint. The pg-erd candidate is invoked explicitly and has source acceptance under the same uid/gid 65532, read-only-root, capability-drop and `no-new-privileges` contract. That remains source evidence until the exact-current-head OCI job executes terminal-success.

## Cutover and rollback

A consumer migration must keep the last known-good deployment manifest/image digest and its executable legacy characterization. Route and HTTP-policy parity must first be terminal GREEN through the compiled dedicated candidate, then exercised through explicit shadow/canary evidence before production cutover. A source PR or listener-capable binary is not traffic-state evidence.

For TLS/H2 migration, the rollback manifest must preserve the old edge's certificate/SNI/ALPN and HTTP/1 fallback behavior as executable traffic evidence rather than relying on defaults. Canary/shadow credit requires the exact immutable gateway artifact to terminate the protocol itself. If an external legacy edge continues to terminate TLS/H2/H3, that is a transitional topology and not proof that the shared gateway has achieved protocol parity. Rollback restores the previous protected deployment revision and certificate references without transferring certificate ownership into `pingora-gateway`.

Roll back by restoring the exact protected prior deployment revision, not by editing a live container. Certificate management, identity, product authorization/business policy, and security-verdict ownership must remain with their existing bounded owners during edge-runtime rollback.

No consumer may pin `pingora-gateway` until a protected release publishes an immutable image digest and rollback has been rehearsed. The current Dockerfile alone is not a releasable artifact, and the pg-erd candidate additionally needs terminal exact-head image invocation plus routed load/failure evidence before release/canary eligibility. The public supplier path for #46 must also be immutable/released or covered by a separately governed provenance-bound backport before parked-read shutdown correctness/scaling can receive release credit. #51 similarly requires an immutable exact supplier with mixed-protocol RED/GREEN and real listener TLS/H2 evidence before protocol release credit; open #936 is not release authority and HTTP/3 remains unsupported.
