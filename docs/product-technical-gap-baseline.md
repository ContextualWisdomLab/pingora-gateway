# Product / Technical Gap Baseline

This file is the code-current migration baseline for `ContextualWisdomLab/pingora-gateway`. Live protected-branch, PR, review, workflow, release and supplier metadata remain the exact authority. Historical RED/GREEN detail belongs in PRs, commits, workflow receipts, ADRs and `CHANGELOG.md`; this snapshot keeps durable architecture, acceptance and remaining buyer-visible gaps. Mutable current-head SHAs and in-flight run IDs are deliberately not copied here because an evidence-refresh commit would immediately stale its own statement.

## Authority and bounded contexts

`pingora-gateway` owns shared Ingress, Edge Routing, TLS consumption, HTTP Policy, Load Balancing mechanics, Observability, Admin Config and Runtime Isolation behavior that is genuinely edge/runtime responsibility. Product authentication and business logic remain product-owned. Keyverse remains identity authority; Wardnet/EgressWeave remain their policy authorities. The gateway consumes released/versioned contracts or explicit operator transport inputs and does not copy sibling source, issue cross-service SQL, or depend on mutable sibling PR heads.

Generic v1 remains a one-upstream Rust/Pingora process. The bounded `cwl-pingora-pg-erd-migration` process is a separate composition root for the characterized `pg-erd-cloud` route/header contract; it is not a general product-routing DSL. `PgErdMigrationConfig` deliberately denies unknown fields and admits only concrete listener, runtime budget and characterized `backend`/`frontend` transport bindings. Route authority stays compiled into the migration plan rather than becoming operator-configurable product routing. Pg-erd configuration version 2 adds only an explicit Runtime Isolation response-body progress lifetime; version 1 and generic v1 do not silently acquire that semantic.

Proposed **Downstream TLS / Protocol Admission** is a future reusable listener-side bounded context under issue #51 and ADR 0012. It does not exist in generic v1 or pg-erd v1/v2: both production roots still register clear-text Pingora `add_tcp` listeners and every characterized upstream peer remains `ALPN::H1`. A later version may own validated downstream certificate/key references, SNI mapping and ALPN admission only. Certificate issuance/renewal/ACME/private-key custody, Keyverse identity, product authentication/business policy and upstream protocol authority remain with their canonical owners.

### `#29` HTTP/1 protocol-transition admission

WebSocket and other connection-wide HTTP/1 Upgrade semantics are not admitted by generic v1 or the bounded pg-erd contract. Final #29 is ordinarily/non-force based on final #27. A transport-neutral `protocol_transition_policy` treats either an `Upgrade` field or a case-insensitive comma-delimited `upgrade` token in any `Connection` field value as an attempted protocol transition, while rejecting false matches such as `x-upgrade`.

Both Pingora composition roots call the shared delivery guard after gateway-local health handling but before request admission and any route/upstream selection; that is the source-ordering contract. The admitted v1 behavior is HTTP 501 fail-closed, not partial WebSocket support. `tests/protocol_transition_traffic.rs` exercises both compiled listeners with WebSocket-shaped HTTP/1.1 requests, requires exact 501, then observes each dedicated origin listener for a fixed 500 ms post-response window and fails if any connection appears during that window; `/readyz` must remain 200. The 500 ms oracle is deliberately bounded evidence and is not described as proof that an arbitrarily delayed origin connection could never occur.

Final #29 closed exact-head CI, Supply Chain and a fresh exact-current owner technical review after formatter-only and documentation overclaim repairs. Its technical COMMENT is not an independent `APPROVED` governance credit. Descendants may ordinarily/non-force adopt that final tree but must independently reacquire checks/review after any source or documentation movement.

### `#39` pg-erd response-body progress lifetime

This phase ordinarily/non-force adopts final #37 while preserving the historical response-lifetime child as ancestry and reapplying only the valid versioned Runtime Isolation delta. Pg-erd version 2 requires a positive `max_upstream_response_body_ms`; version 1 rejects that field and generic v1 remains unchanged. The budget starts at the first non-informational upstream response header and cannot be reset by later headers. Runtime enforcement checks elapsed monotonic time only on non-empty upstream body progress, so empty/end-of-stream bookkeeping callbacks cannot manufacture a timeout. A non-empty progress callback at or beyond the configured budget becomes an upstream-scoped fatal error. If status/framing is already committed, the gateway terminates the incomplete response rather than inventing a second status, retry or failover.

`tests/pg_erd_slow_drip_response_traffic.rs` separates this control from Pingora `read_ms`: the characterized backend delays 150 ms before committing HTTP 200 with `Content-Length: 20`, then writes one byte every 60 ms while `read_ms` is 500 ms and version 2 declares a 300 ms body-progress lifetime. Acceptance requires the downstream to survive at least the header-delay plus body-lifetime lower bound, terminate before the full 20-byte drip can complete, preserve exact committed 200/framing, record exact request-error telemetry, keep `/readyz` healthy, and permit later independent frontend recovery. Traffic/metrics reservations are simultaneous; origin reads are bounded to five seconds/64 KiB; HTTP status, `Content-Length`, and Prometheus metric oracles reject protocol/name/numeric-prefix lookalikes. This is deliberately a progress-driven bound, not an exact timer interrupt of a currently pending read. Incomplete response-header slow delivery and broader admitted long-lived-stream semantics remain separate gaps. Final #39 has terminal unchanged-head CI/Supply Chain and current-range technical evidence. ADR 0010 remains Proposed pending the broader protected promotion/governance path.

### `#47` supplier-bound parked-read graceful-shutdown projection

This documentation-only successor ordinarily follows final #44 and does not copy Pingora proxy internals or consume a mutable contributor branch. It keeps #46 separate from the three header controls above and from #20's already-admitted in-flight SIGTERM drain proof.

### `#53` executable H2-to-H1 Cookie supplier RED

The mixed-protocol child now has real-wire supplier evidence rather than documentation-only projection. A Linux test composition consumes the shared gateway proxy and the pinned Pingora supplier, terminates downstream TLS with H2 enabled, keeps the characterized upstream on HTTP/1.1, and proves the client emitted two distinct HTTP/2 `Cookie` fields before the Pingora boundary. The raw H1 origin then requires exactly one `Cookie` field joined with `"; "`; the pinned supplier instead forwards the two values as two H1 fields. This is the intended RFC 9113 §8.2.3 supplier RED, not a TLS/bootstrap/client or fixture failure.

The fixture remains bounded and evidence-oriented: inherited listener transfer is explicitly nonblocking, origin header accumulation is capped at 64 KiB, helper lifecycle is finite, and client/origin preconditions must succeed before the protocol oracle can fail. Independent load, bounded-origin capacity, OCI and Supply Chain lanes are GREEN on the same current source state, but they do not convert the mixed-protocol test RED into protocol GREEN; the failing test job also earns no later lint/rustdoc/coverage/lock credit after the supplier assertion terminates it.

Current public Pingora places automatic request-header forwarding under `HttpUpstreamRequestPolicy` and calls `sanitize_h1_upstream_request(...)` from the H1-upstream path. That sanitizer currently receives only a `downstream_is_http11` boolean. A supplier repair must not infer exact H2 input from `!downstream_is_http11`; the Cookie rule is H2-specific and needs an exact source-protocol/version predicate at the normalization boundary. A narrow default-on Cookie-normalization option may live in the current request-policy aggregate, but its compatibility opt-out must not require broad `preserve()` semantics or disable Connection/hop-by-hop protections. Mutable #901 remains owner-path evidence only until normally adapted, maintainer-integrated and released immutably.
