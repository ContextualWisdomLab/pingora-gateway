# Context Map

| Context | Type | Owns | Relationship |
| --- | --- | --- | --- |
| Edge Contract | Supporting | Versioned active configuration, explicit upstream authority, request-body budget, timeout/TLS invariants | Upstream of Startup/Activation and Pingora Delivery; active v1 remains one-upstream-per-process |
| Edge Routing | Supporting characterization | Deterministic exact/prefix path selection among explicitly named upstream identities, precedence and fail-closed ambiguity | Consumer-derived shared-edge contract; transport-neutral; consumed by the pre-listener migration callback |
| HTTP Policy | Supporting characterization | Explicit edge-owned HTTP response field identity/value contracts and RFC 9110 fail-closed validation | Separate from Edge Routing and product response semantics; transport-neutral; consumed by the pre-listener migration callback |
| Ingress Forwarding Policy | Supporting | Trust transition from accepted downstream transport/request authority to legacy compatibility forwarding fields | Removes request-controlled proxy identity before rebuilding only characterized `X-Forwarded-*`/`X-Real-IP` values; owns no identity/auth/product truth |
| Migration Delivery | Generic adapter | One-to-one binding from admitted migration upstream identities to explicit validated Pingora peers | Downstream of `migration_plan` application composition and Edge Contract `UpstreamConfig`; rejects missing/duplicate/undeclared authority |
| Runtime Isolation | Supporting | Non-zero request-body and process in-flight admission budgets | Shared by active `GatewayProxy` and pre-listener `MigrationGatewayProxy`; independent of routing/product policy |
| Observability | Supporting | Low-cardinality request completion observation, gateway counters, and payload-free access-log shape | Shared by both Pingora adapters; excludes paths, headers, cookies, credentials, customer payloads, and product identifiers |
| Startup/Activation | Application | `--config` parsing, file loading, validation-before-listen, process composition | Currently activates v1 Edge Contract + `GatewayProxy`; multi-route activation requires a later explicit versioned transition |
| Pingora Delivery | Generic adapter | `HttpPeer`, proxy callbacks, health response, forwarding distrust, streamed-body enforcement | Conformist to Pingora, downstream of admitted edge contracts |
| Migration Callback | Generic adapter | `MigrationGatewayProxy` composition of characterized routing/HTTP policy, explicit peer binding, transport-derived forwarding trust, runtime isolation, and shared observability | Pre-listener only; no shadow/canary/cutover claim until Startup/Activation explicitly admits it |
| Consumer Product | External bounded context | Product routes and semantics, static behavior, authentication/authorization, business policy, domain state | Supplies legacy-edge behavior for characterization where responsibility is truly shared; never imported here |
| Wardnet / EgressWeave | External security contexts | Security verdicts and canonical network/security policy owned there | Referenced boundary only; not reimplemented in HTTP Policy or forwarding trust |
| Keyverse | External identity context | Canonical identity/credential authority | Referenced boundary only; not reimplemented here |
| Certificate Management | External operational context | Issuance, renewal, storage, rotation | Supplies trust material/platform TLS as appropriate; not owned by this runtime |

`migration_plan` is application-level composition across validated Edge Routing, HTTP Policy, and an explicit stable upstream-identity set. It is not an additional bounded context and does not grant network authority. `migration_delivery` binds those admitted stable identities to explicit Pingora peers, while `migration_proxy` composes those bindings in `ProxyHttp` callbacks, derives current pg-erd compatibility forwarding fields from accepted transport/request metadata, and delegates transport telemetry to `observability`.

The current pg-erd characterization covers the clear-text Traefik `web` entryPoint; TLS-derived forwarding scheme is a later listener/TLS contract and is not inferred here. None of the migration composition activates multi-route production traffic: current Startup/Activation still selects `GatewayProxy`. A later explicit versioned startup/configuration transition must admit multi-route serving and then prove parity, shadow/canary, rollback, and cutover evidence. There is no shared Rust product-domain model with consumer products, Context Graph, Enterprise Architecture, Wardnet/EgressWeave, or Keyverse.
